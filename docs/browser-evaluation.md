# Browser Automation Evaluation

This experiment evaluates MacJev as an action selector, not as a browser
executor. The model receives a goal, a structured page/DOM snapshot, and an
indexed candidate action set. It returns one action label. The executor,
selector validation, stale-target checks, navigation, and form mutation remain
outside the model.

## Action Evaluation

The fixture uses local static page states. It measures:

- exact action accuracy
- top-two accuracy from the returned probability distribution
- valid-target rate
- errors by scenario

The first fixture covers search and form trajectories. It does not use
screenshots, live accounts, network pages, selectors generated by the model,
coordinates, JavaScript, or shell commands.

Run:

```bash
PYTHONPATH=src:. python3 -m playground.evaluate_browser \
  --dataset fixtures/browser-actions-v1.jsonl \
  --output runs/browser-actions-v1
```

For a reproducible three-repeat Metal run:

```bash
PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=src:. \
python3 -m playground.evaluate_browser \
  --dataset fixtures/browser-actions-v1.jsonl \
  --output runs/browser-actions-v2-samples1-r3 \
  --upstream http://127.0.0.1:8080 \
  --timeout-seconds 180 \
  --run-id browser-v2-s1-r3-20260919 \
  --repeats 3
```

## Continuous Context A/B

The same rows are evaluated in four modes:

- `fresh_schema`: every step has a new question ID and no trajectory history.
- `stable_schema`: one question schema is reused with only the current page.
- `continuous_history`: the stable schema is reused and the state appends the
  labelled prior observation/action trajectory.
- `schema_churn_history`: the same labelled trajectory history is retained,
  but the question ID changes every step.

Each run uses a unique schema namespace so a previous benchmark cannot supply
the first request's KV cache.

Repeated runs use separate trajectory identities. Context comparisons report
both all rows and follow-up rows; the follow-up slice excludes each
trajectory's cold first request.

The phase benchmark fixes `samples` to `1`. The production default is `auto`,
which may run one or four samples depending on entropy; leaving that enabled
would mix diffusion sampling decisions into the context-reuse comparison.

The comparison is phase-specific:

- `prompt_tokens`: rendered prompt size
- `reused_tokens`: resident KV prefix reused by DiffusionGemma
- `prefill_ms`: prompt/context encoding into KV
- `non_prefill_ms`: complete request minus prefill
- `denoise_ms`: structured diffusion forward
- `complete_ms`: wall-clock request time

The expected signal is not assumed. A continuous-context advantage is only
reported if the observed `reused_tokens` and `prefill_ms` support it. Denoise
is reported separately because KV reuse should not be treated as a denoise
speedup.

The benchmark runs against an already started local Metal service. It does not
measure model loading or process startup, and it does not claim production
browser reliability from static fixtures.

The first real run and its interpretation are recorded in
[Browser Evaluation Results](browser-evaluation-results.md).
